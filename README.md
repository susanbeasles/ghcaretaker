# GitHub caretaker capability

Audited, repository-scoped GitHub read and collaboration tools. Authentication, OAuth, owner approval and navigation are owned by the shared control plane at https://control.vespoli.me/owner/apps/caretaker.

Canonical integrated source: https://github.com/susanbeasles/personal-control, under `workers/ghcaretaker`. This repository remains the compatible component mirror. Changes to this capability must be synchronized into that component tree before a central release; gateway UI and owner authentication remain in Personal Control's top-level `src/`.

The public worker delegates MCP authentication to the shared gateway. `CaretakerCapability` exposes focused private service methods; it does not issue sessions or manage an independent login. App credentials remain in the existing AppVault Durable Object. Setup redirects to the shared owner pane.

Run `npm ci --ignore-scripts`, the explicit `npm rebuild esbuild workerd --ignore-scripts=false --foreground-scripts`, `npm run check`, `npm test`, and `npm run build`. The build is local packaging only. The old `npm run deploy` entrypoint stops without making provider calls: deployment requires the existing `workflow_depot` authorization and `delivery_control` execution path, including explicit treatment of database migrations. Existing Cloudflare resource bindings and Durable Object state must be retained.

New clients connect to `https://control.vespoli.me/mcp/caretaker`; the legacy MCP path delegates to that same gate. Existing independent OAuth grants require authorization again through the shared issuer.

The private capability exposes `status`, `begin`, `convert`, `install`, `manifest`, `tools`, `mcp`, `callTool`, and `webhook`. Only the central gateway publishes `/webhooks/github/caretaker`, forwarding the original JSON bytes to `webhook`. The existing AppVault verifies GitHub's SHA-256 HMAC with its retained manifest webhook secret. Webhook machine authentication does not issue an owner session. The legacy public component route does not expose this method.

Authenticated issues, pull requests, repository events and Actions events produce a metadata-only receipt: delivery ID, event, action, repository name and local receive time. Raw payloads, issue text and credentials are not stored in the receipt ledger. Status returns the latest 20 receipts and accepted count. Normal deduplication keeps at most 1,024 delivery records for seven days and refuses excess unique deliveries until records expire; a separate bounded critical record lets signed suspension or deletion invalidate authority even when ordinary receipt capacity is full. Events never trigger GitHub collaboration, workflow dispatch, source writes or deployment.

Suspension or deletion puts the vault into `installation-review-required`. An explicit owner **Verify installation** action checks the current GitHub App, numeric owner, installation and permissions before restoring access. An invalidation arriving during that verification prevents stale reactivation. A signed unsuspend or create event alone cannot enroll or enable an installation. As GitHub delivery timestamps are not a signed freshness guarantee, delayed valid suspension evidence stops access conservatively until a fresh owner verification.

Repository grants are enforced before any GitHub request. Installation tokens carry the same repository restriction, and repository-list results are filtered to the grant. Account-wide audit tools require the owner-wide repository grant because historical audit records may contain other repositories' data. Contents and Actions remain read-only; writes are limited to the existing issue and pull-request collaboration tools, without automatic retries.

`status().webhook.configured` means the existing vault contains a usable webhook secret. It does not prove a live delivery, an installed App, or a deployed version. Activation uses the existing App and stored secret: deploy the reviewed gateway and capability through the central path, set that App's webhook URL to `https://control.vespoli.me/webhooks/github/caretaker` with the generated manifest's events, and verify an authenticated delivery appears in the owner pane. Do not create another App or copy its secrets into developer tooling. If the retained secret is absent, its existing secure setup must be reconciled before webhook activation.

Implementation references: [GitHub webhook signature verification](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries), [GitHub installation events](https://docs.github.com/en/webhooks/webhook-events-and-payloads#installation), and [Cloudflare private Worker service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/).
